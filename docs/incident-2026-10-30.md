# Incident report: the BIOS update of 30/10/2026

This report tells what happened, how it was solved with Windows tools only, and why certain choices were made. The procedure to follow is in the [guide, Phase 7](guide.md#phase-7--if-the-ssd-disappears-from-the-f12-menu-after-a-bios-update-or-reset); the short version for emergencies is in [quick-recovery.md](quick-recovery.md). As in the rest of the repository, observed facts are kept apart from interpretations.

---

## Summary

On 30/10/2026, while an installation was running on the external Windows, a BIOS update started. The BIOS went back to its default settings, `ThunderboltBoot` included, and the external SSD disappeared from the F12 menu. The very probable cause is Dell SupportAssist, which had reached the external Windows without our choosing it.

Ubuntu was no longer available, so the repair was done with Windows tools only. The enclosure was connected in USB mode to reach the Windows Recovery Environment (WinRE), and from there `ThunderboltBoot` was turned back on through the BIOS WMI interface. Windows started again via Thunderbolt. Then the Dell software was uninstalled and blocked.

## Cause

**Very probable, not certain:** Dell SupportAssist, installed on the external Windows without the user choosing it. On 30/10 these were installed:

| Program | Version | Installation date |
|---|---|---|
| Dell Connected Service Delivery + SubAgent | 1.1.2 | 05/10 |
| Dell Core Services | 1.15.18 | 07/10 |
| Dell SupportAssist | 5.2.5 | 24/10 |

Dell Command Update was not installed.

**Observed facts.** Connected Service Delivery is a software component (class *SoftwareComponent*) attached to a dedicated Dell ACPI device, `ACPI\DELL0033`, and brings the rest with it. The policy that excludes drivers from Windows Update (`ExcludeWUDriversInQualityUpdate = 1`, guide step 5.1) was in effect, verified on 30/10.

**Interpretation.** That policy only acts on Windows Update: it does not stop SupportAssist from updating the BIOS on its own. How Connected Service Delivery arrived on 05/10, the day of the installation, has not been established.

**Open question.** We do not know whether every BIOS update resets the settings to their defaults, or whether it happened because of the SPI error.

---

## Diagnosis

1. **The SSD does not appear in the F12 menu.** This is the symptom of `ThunderboltBoot` being off: without it, the firmware does not create the Thunderbolt tunnel before boot and does not see the SSD ([how-it-works.md](how-it-works.md), section 2). Reading it with `wmic` later confirmed it: `Disabled`.
2. **Ubuntu was not available.** The `scripts/thunderbolt-boot.sh` script could not be used, and a Windows-only route was needed.
3. **The first obstacle was the cable.** Connected with a USB-C cable to a Thunderbolt port, the enclosure negotiates Thunderbolt anyway, and the firmware does not see it. Only with a USB-C → USB-A cable on a USB-A port does the enclosure work in USB mode, and *UEFI Realtek ACASIS …* appears in the F12 menu.
4. **In USB mode Windows does not start**: `INACCESSIBLE_BOOT_DEVICE`. The cause has not been established. **The recovery environment, on the other hand, starts and works**, and sees the Windows partition after the recovery key is entered.
5. **The recovery environment has no PowerShell**, but it has `wmic` and `cscript`. With `wmic` the `ThunderboltBoot` attribute shows up in the updated BIOS too, with the value `Disabled`.
6. **The registry was already fine.** The repair script found `0x0`, `0x0`, `0x14`: the only problem was `ThunderboltBoot`.

## Solution

Only what worked, in order.

1. Enclosure connected with the **USB-C → USB-A cable to a USB-A port**: USB mode, and the *UEFI Realtek ACASIS …* entry in F12.
2. Booting from that entry: Windows does not start, but after the failed attempts Automatic Repair appears, and **the recovery environment starts**. BitLocker asks for the recovery key; once it is entered, the volume is already unlocked in the prompt.
3. From the Automatic Repair screen: **Advanced options → Troubleshoot → Advanced options → Command Prompt**. The Windows drive was `D:`; `X:` is the recovery environment.
4. `D:\Repair\repair-usb4-boot.bat`, in the version present at the time: it found the values already correct (`0x0`, `0x0`, `0x14`), wrote them again, checked them and unloaded the registry. **The script's offline mode is verified in WinRE.**
5. Reading `ThunderboltBoot`:
   ```
   wmic /namespace:\\root\dcim\sysman\biosattributes path EnumerationAttribute where "AttributeName='ThunderboltBoot'" get AttributeName,CurrentValue
   ```
   Result: `Disabled`.
6. Writing with a VBScript typed in `notepad`, run with `cscript //nologo D:\Repair\thunderbolt-boot-on.vbs`: `Status = 0`, and reading back with `wmic` gave `Enabled` straight away. The script is shown in the guide, step 7.2. Typo encountered: `0.ExecMethod_` (zero) instead of `o.ExecMethod_`.
7. `exit`, then **Turn off your PC**. Enclosure reconnected with the Thunderbolt cable to the Thunderbolt port; in F12 *UEFI WD_BLACK SN850X …* was back, and **Windows started via Thunderbolt**.
8. In Windows: BitLocker protection turned back on with `manage-bde -protectors -enable C:`, and boot order fixed with `bcdedit`, because Windows had recreated its own entry and put it in first place.

### Why USB mode

With `ThunderboltBoot` off, the firmware does not see the SSD via Thunderbolt, so it can start neither Windows nor its recovery environment. The ACASIS enclosure, however, has two chips: a Thunderbolt controller (JHL7440) and a USB bridge (Realtek RTL9210B). In USB mode the SSD is an ordinary USB drive, which the firmware can boot by itself. Windows does not start in that mode, but it is enough for the recovery environment to start, and from there the BIOS attribute can be changed. USB mode is useful for this only.

### Why WMI from the recovery environment

The Linux script `thunderbolt-boot.sh` uses `dell-wmi-sysman`, which exposes the attributes of the Dell BIOS WMI interface. Windows reaches the same interface in the `root\dcim\sysman\biosattributes` namespace: the `EnumerationAttribute` class for reading, the `SetAttribute` method of the `BIOSAttributeInterface` class for writing. The recovery environment has no PowerShell, but it has `wmic` to read and `cscript` to run a VBScript that writes.

**Interpretation:** the interface is exposed by the firmware through the ACPI-WMI driver built into Windows, not by a Dell driver. This is suggested by the fact that it works in the recovery environment, where there are no Dell drivers.

## Prevention

Applied on 30/10 on the external Windows, in PowerShell as administrator (guide, step 5.10).

1. **Uninstallation** with `winget uninstall --name "<name>" --exact`, all successful: "Dell SupportAssist", "Dell Core Services", "Dell Connected Service Delivery SubAgent", "Dell Connected Service Delivery".
2. **Blocking the devices** with the `DenyDeviceIDs` policy, the same one that blocks the VMD driver (guide, step 5.5.2). Result: 1 = the VMD controller's ID, 2 = `SWC\VID001&PID0001&DCSDSoftware`, 3 = `ACPI\DELL0033`.
3. **Removal** of the two devices and their driver packages (`dcsdsoftware.inf`, `dcsddriver.inf`) with `pnputil /remove-device` and `pnputil /delete-driver ... /uninstall /force`.

### Why block `ACPI\DELL0033`

Connected Service Delivery is a software component attached to the `ACPI\DELL0033` ACPI device, and brings the rest with it. Uninstalling the programs is not enough if the component can come back by attaching itself to that device again. By blocking the device's ID and the component's (`SWC\VID001&PID0001&DCSDSoftware`), Windows can no longer install drivers for either. This is an interpretation: whether the block holds over time is still to be verified.

## Lessons

- **The cable decides the mode.** With this enclosure, a USB-C cable on a Thunderbolt port always negotiates Thunderbolt. USB mode needs a USB-C → USB-A cable on a USB-A port. Keep one at hand.
- **In WinRE, never *Continue*.** *Continue* starts the firmware's default entry, that is the internal system. It really happened, with the enclosure connected and BitLocker protection suspended. Always *Turn off your PC*, then F12.
- **PowerShell commands in Command Prompt.** This was the most frequent mistake. In WinRE there is no PowerShell at all; in Windows, every block of commands in the guide now says where to run it.
- **`0.ExecMethod_` instead of `o.ExecMethod_`.** When typing a VBScript by hand, zero and the letter o get mixed up. Better to have the scripts ready in `C:\Repair\`.
- **A BIOS update suspends BitLocker.** It must be turned back on by hand, and until then the SSD is readable by any system.
- **The Windows Update policy is not enough.** The manufacturer's software can update the BIOS on its own: check for it with `winget list Dell` and block it.
- **It can be done without Ubuntu.** Both of Ubuntu's tasks have a Windows equivalent verified in WinRE: the VBScript for `ThunderboltBoot` and the script's offline mode for the registry.
